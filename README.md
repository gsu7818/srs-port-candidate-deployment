## 先选延迟，再谈部署

部署 SRS 的第一个决定不是装哪个版本，而是你能接受几秒延迟——这个选择决定了要开哪些协议。SRS 用同一个 C++ 二进制同时支持 RTMP、WebRTC、HLS、HTTP-FLV 和 SRT，配置里开哪个 listener，就多一种播放方式。

| 协议 | 典型延迟 | 依赖端口 | 适合场景 |
| --- | --- | --- | --- |
| HLS | 5–15 秒 | 8080/TCP | 兼容性优先，任何播放器都能放 |
| HTTP-FLV | 1–3 秒 | 8080/TCP | 浏览器播放，需一个小播放器库 |
| WebRTC | 1 秒以内 | 8000/UDP | 互动直播、连麦、低延迟监控 |
| SRT | 取决于链路 | 10080/UDP | 弱网环境下的回传 |

多数人第一步只需要 RTMP 推流加 HLS 或 FLV 播放，WebRTC 等链路跑通之后再开。

## 服务器准备：先把带宽和磁盘算清楚

SRS 的内存占用比很多人预期低，512MB 对少量流来说相当宽松，CPU 更是只有开转码时才值得关心。真正要提前算的是带宽和磁盘，这两项决定你的账单。

磁盘按码率算：一路 6 Mbps 的流录一小时约 2.7 GB，24 小时不停就是 60 多 GB。开 DVR 之前先想清楚要保留多久，比事后清理省事。

带宽按观众算：每个观众单独占一份下行，10 个人看 6 Mbps 的流，出方向就是 60 Mbps。云服务器按固定带宽计费时，这笔账要在开机器前算完。

## Docker 部署：一条命令，五个端口

最快的部署方式是官方 Docker 镜像，一条命令把所有端口映射出来：

bash
docker run --rm -it -p 1935:1935 -p 1985:1985 -p 8080:8080 \
  -p 8000:8000/udp -p 10080:10080/udp ossrs/srs:6


每个端口各管一摊：

| 端口 | 协议 | 用途 |
| --- | --- | --- |
| 1935 | TCP | RTMP 推流 |
| 1985 | TCP | HTTP API |
| 8080 | TCP | HLS、HTTP-FLV、内置控制台 |
| 8000 | UDP | WebRTC 媒体 |
| 10080 | UDP | SRT |

启动后访问 `http://服务器IP:8080/`，能看到内置控制台就说明服务正常。生产环境建议改用 docker-compose，加上 `restart: unless-stopped`，并通过环境变量设置 CANDIDATE（下一节专门讲）。

镜像版本值得说一句：`:6` 是当前的稳定线，最新补丁 v6.0-r2 于 2026 年 9 月 24 日发布。`:7` 是 7.0 的首个开发版 v7.0-d0，带来了 RTSP 播放、RTMPS、IPv6、HLS fMP4 等新特性，也移除了一些旧功能，比如嵌入式 GB28181 SIP 服务器和大部分配置热重载。新项目尝鲜可以试 7，跑生产还是用 6 稳妥。

## CANDIDATE：WebRTC 黑屏的元凶

WebRTC 播放黑屏，绝大多数是 CANDIDATE 没设对。WebRTC 客户端需要知道该往哪个 IP 发媒体流，而容器里的 SRS 只能看到私有地址。这个变量必须填浏览器真正能访问到的 IP：公网观众填公网 IP，局域网测试填内网 IP。

填错的症状很典型：1985 端口的信令一切正常，8000 端口的媒体流却哪里都没去。如果观众在严格 NAT 后面，还需要额外的 TURN 服务器，SRS 本身不带。

调试顺序建议反过来：先用 HTTP-FLV 确认推流、服务、端口整条链路是通的，再开 WebRTC。FLV 不存在地址广播问题，能播就说明前面都没问题，剩下只需排查 CANDIDATE 这一项。

## 推流和播放：用三条 URL 验证全链路

推流端在 OBS 里选「自定义」服务，服务器填 `rtmp://你的IP/live`，流密钥填 `livestream`，即可开播。不想装 OBS 的话，FFmpeg 一条命令也能代替：

bash
ffmpeg -re -i ./doc/source.flv -c copy -f flv -y rtmp://你的IP/live/livestream


播放按延迟从高到低依次验证：

- HLS：`http://你的IP:8080/live/livestream.m3u8`
- HTTP-FLV：`http://你的IP:8080/live/livestream.flv`，网页里需要支持 FLV 的播放器
- RTMP：`rtmp://你的IP/live/livestream`，VLC 直接打开
- WebRTC：从 8080 控制台进入对应的播放页

控制台会直接显示推流端、观众数和码率，不需要另外装监控。

## 录制、API 与回调：别让 1935 端口暴露到公网

DVR 开启后，SRS 会把每路会话写成 MP4 或 FLV 文件，支持按时间或大小切片；1985 端口的 HTTP API 可以列出当前流和客户端，也能踢掉推流端。这两项配置都不复杂。

真正要重视的是访问控制。SRS 的鉴权只有 HTTP 回调一条路：推流、断流、播放、录制完成时，它会向你的接口发请求，接口返回非 200 就拒绝推流。也就是说，在把 1935 端口暴露到公网之前，先把回调鉴权接上。否则任何人猜到推流地址，都能往你的服务器上推内容。

## 部署完别忘了算总成本

转码是 CPU 密集型操作，如果观众不需要多码率，一直关闭最省钱。带宽随观众数线性增长，这也是为什么小范围内部分享用一台入门机器就绰绰有余，面向公众的大规模直播则要考虑 CDN 回源。把转码、录制、带宽三项分开算，才知道钱花在哪。

## 常见问题

**SRS 和 MediaMTX 怎么选？**

MediaMTX 是单个 Go 二进制，YAML 配置扁平，英文文档更完整，还支持 SRS 没有的 RTSP。SRS 强在 WebRTC 成熟度、内置控制台和转码钩子，社区规模也更大。浏览器里要亚秒级播放，选 SRS；只需要 RTSP/RTMP 转发，MediaMTX 配置起来更省事。

**HLS 延迟能压到 1 秒吗？**

标准 HLS 延迟在 5–15 秒。LL-HLS 目前只出现在 7.0 开发版里，稳定版想降延迟，更实际的做法是用 HTTP-FLV 或 WebRTC。

**512MB 内存能跑几路流？**

不转码的情况下，几路流没问题，瓶颈通常在带宽和磁盘，不在内存。

**WebRTC 必须用公网 IP 吗？**

CANDIDATE 必须是浏览器能访问到的地址。局域网测试用内网 IP 即可，公网观众需要公网 IP；NAT 严格时还要加 TURN。

## 按你的情况做最后决定

只求兼容性、延迟无所谓：开 HLS，最省心。要浏览器里 1–3 秒：用 HTTP-FLV。要亚秒互动：上 WebRTC，先配好 CANDIDATE，再考虑 TURN。准备录制：按码率先算磁盘，6 Mbps 一小时就是 2.7 GB。
